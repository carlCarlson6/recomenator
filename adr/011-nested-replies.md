# ADR 011: Nested Replies (Reddit-style Threading)

## Status

**Accepted / Implemented**

## Context

The app previously supported only flat, top-level replies on recommendation posts. Users needed the ability to reply directly to an existing reply, creating threaded discussions similar to Reddit. The goal was to preserve the existing reply concept, support unlimited nesting in the data model, and render threads with familiar visual indentation without breaking mobile layouts.

## Decisions

### 1. Keep "reply" naming and unlimited nesting

- The feature remains "replies" rather than being renamed to "comments."
- The database allows arbitrary depth via a self-referencing foreign key; the UI caps visual indentation after six levels to keep mobile readable.

### 2. Data model

- Added `parentId` (nullable) to `replies` with a self-referencing FK (`onDelete: 'no action'`) so child replies survive parent deletion.
- Added `deletedAt` (nullable timestamp) to support soft deletion.
- Kept `postId` denormalized on every reply so reply counts, timelines, and group unread counts continue to work without traversing the tree.

### 3. Deletion semantics

- Only the reply author can delete their own reply, matching the existing `deletePost` authorization rule.
- Deletion is soft: the reply is marked with `deletedAt` and remains visible as `[deleted]` so children are not orphaned.
- Replying to a deleted reply is rejected.

### 4. Domain and application layer

- `Reply` now carries `parentId` and `deletedAt` and exposes a `delete()` method.
- New domain errors: `ReplyNotFoundError`, `ReplyToDeletedReplyError`, `ReplyPostMismatchError`.
- `ReplyRepository` gained `findById`; `save` uses `insert … onConflictDoUpdate` to handle both creation and soft-deletion updates.
- `addReply` validates the parent reply exists, is not deleted, and belongs to the same post.
- `listReplies` fetches a flat list ordered by `createdAt`, enriches it with author display names, and builds a `ReplyNodeDto` tree with `children` and `depth`.
- Added `deleteReply` use case with author-only authorization.

### 5. UI/UX

- Each reply renders a "Reply" link that toggles an inline `ReplyForm` scoped to that parent.
- Child replies are rendered inside a nested wrapper (`ml-2 pl-3 border-l-2 border-border`) per level, producing Reddit-style indentation with a continuous vertical thread line. Only static Tailwind classes are used, because dynamically composed class names (e.g. `ml-${n}`) are never generated by Tailwind.
- Nesting stops indenting after six levels and shows a "Thread continues below" cue so mobile stays readable.
- Threads can be collapsed and expanded per reply.
- Deleted replies show `[deleted]` for both author and content but continue to render their children.
- The delete action is shown only to the author and immediately invalidates the replies query.

### 6. Tests

- Added `test/modules/replies/domain/Reply.test.ts` for creation, nesting, validation, deletion, and reconstitution.
- Added `test/modules/replies/application/ReplyUseCases.test.ts` covering top-level and nested replies, parent validation, tree building, deleted parents, and author-only deletion.
- Updated `test/modules/posts/application/ListMyInteractions.test.ts` to satisfy the extended `ReplyRepository` interface.

## Consequences

- Users can have threaded conversations on any recommendation.
- The existing group unread badge and post reply counts continue to work because nested replies retain `postId`.
- Soft deletion preserves conversation context while allowing users to remove their own content.
- The six-level visual cap prevents unreadable indentation on narrow mobile screens while still allowing deeper nesting in the data model.
- The seed script creates one nested reply so threading is visible immediately after `npm run db:seed`.
